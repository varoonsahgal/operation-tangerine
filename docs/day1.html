🧩 Module 1 · The agentic data layer

An AI agent is a model in a loop: it reads a request, decides which tool to call, reads the result, and repeats until it can answer. The model reasons, but everything it knows about your business comes from the data layer. If that layer is broken, the agent gives wrong answers or no answers.

🛠️ Tools → operational data

Structured facts: customers, orders, products. Here that's Aurora PostgreSQL, queried with SQL through the RDS Data API.

📚 Knowledge → retrieval

Unstructured documents (policies, guides) chunked, embedded and stored as vectors, then searched at question time. That's retrieval-augmented generation (RAG): Bedrock Knowledge Base → pgvector in Aurora.

🧠 Memory → state

What was said, what the agent is working on, what it learned about the user. Fast key-value access: DynamoDB.

🔭 Observability → debugging

Logs, metrics and MCP servers that let you (or another AI) inspect the databases while the agent runs.

The story so far Citrus & Co. sells 200,000 products to 5,000 customers. Support staff ask Zest things like "Why is customer C00042 upset, and are they covered by warranty?" Zest answers through 10 Lambda actions: SQL tools (search_products, customer_profile), search_docs, similar_notes, memory tools, health, and ask, the Claude agent loop that ties them together. Last night a "cost-saving refactor" broke half of them. That's the exam scenario in a nutshell.

Follow the request

Every failure you'll debug this week sits on one hop of this path. Learn the hops and you can find the break.

  1. Invoke: something calls the Lambda (you, a test, an API).
  2. Identity: Lambda runs as its execution role. Every AWS call it makes is checked by IAM.
  3. Configuration: env vars tell the code which cluster, secret, table and Knowledge Base to use.
  4. Credentials: the Data API fetches DB credentials from Secrets Manager as the caller.
  5. Service endpoint: the Data API must be enabled; the table must exist; the KB must be synced.
  6. Database: the DB user needs privileges; the schema, extensions and indexes must be right.
  7. Result: logs and metrics in CloudWatch tell you how it went.
Exam lens The exam lab is a multi-fault scenario: several hops are broken at once, across different services. Fixing hop 2 often reveals that hop 5 was also broken. That's normal. Keep following the request.

🛡️ Module 2 · IAM for agents

In every exam challenge, part of the question is: who is calling, and are they allowed? IAM answers that for every API call.

Principal

Who is calling: a user, or a role assumed by a service. Our Lambda runs as …-zest-agent-role.

Trust policy

Who may assume a role. Lambda's role trusts lambda.amazonaws.com; the KB role trusts bedrock.amazonaws.com.

Permissions policy

What the role may do: actions × resources (× conditions). Identity-based, attached to the role.

Resource policy

Attached to the resource (S3 bucket, secret, KMS key). Can grant or deny cross-account. Optional here.

How AWS decides

Read the AccessDenied message. It tells you the fix.

User: arn:aws:sts::111122223333:assumed-role/tangerine-student1-zest-agent-role/tangerine-student1-zest-agent
is not authorized to perform: dynamodb:PutItem
on resource: arn:aws:dynamodb:us-east-1:111122223333:table/tangerine-student1-agent-memory
because no identity-based policy allows the dynamodb:PutItem action

Four facts in one line: the principal (the Lambda role), the action, the resource, and the reason ("no identity-based policy allows" means add an Allow to the role; "explicit deny" means find and fix a Deny).

Who needs what in Zest's world

Classic gotchas
  • DynamoDB GSIs are separate resources: …/table/name/index/*. Query on a GSI fails if only the table ARN is listed.
  • s3:ListBucket goes on the bucket ARN; s3:GetObject goes on bucket/*.
  • IAM changes are eventually consistent. Wait 5–10 seconds before retesting.
LAB 1.3

IAM Detective

⏱ 25 min🍊🍊 Medium

🎯 Read Zest's two roles like an auditor, and predict IAM decisions before testing them with the policy simulator.

  1. Who can assume the Lambda role? Look at its trust policy: 
    aws iam get-role --role-name "$LAMBDA_ROLE_NAME" --query Role.AssumeRolePolicyDocument
  2. What may it do? List attached managed policies and read the inline policy: 
    aws iam list-attached-role-policies --role-name "$LAMBDA_ROLE_NAME"
aws iam get-role-policy --role-name "$LAMBDA_ROLE_NAME" --policy-name agent-data-access
  3. Predict first, then simulate: which of these does the Lambda role allow on the memory table? dynamodb:PutItem, dynamodb:Scan, dynamodb:DeleteTable 
    aws iam simulate-principal-policy \
  --policy-source-arn "$LAMBDA_ROLE_ARN" \
  --action-names dynamodb:PutItem dynamodb:Scan dynamodb:DeleteTable \
  --resource-arns "$MEMORY_TABLE_ARN" \
  --query 'EvaluationResults[].[EvalActionName,EvalDecision]' --output table
  4. Can the Lambda read the Knowledge Base's secret? Predict, then simulate. (Remember the answer for Lab 1.7.) 
    aws iam simulate-principal-policy --policy-source-arn "$LAMBDA_ROLE_ARN" \
  --action-names secretsmanager:GetSecretValue --resource-arns "$KB_USER_SECRET_ARN" \
  --query 'EvaluationResults[].EvalDecision'
  5. Open the KB service role's trust policy. What do the aws:SourceAccount and aws:SourceArn conditions protect against? 
    aws iam get-role --role-name "$KB_ROLE_NAME" --query Role.AssumeRolePolicyDocument
Hint for step 5
Search for "confused deputy". Without the conditions, another account's Bedrock resource could trick the Bedrock service into using your role.
Answers
  • Trust: only lambda.amazonaws.com may assume the role.
  • PutItem: allowed. Scan and DeleteTable: implicitDeny. The agent never needs to scan or drop tables, so it can't (least privilege).
  • KB secret: implicitDeny. The AuroraSecret statement lists only the admin secret.
  • The conditions stop the confused-deputy problem: Bedrock may assume the role only for Knowledge Bases in your account.
You can say in one sentence each what a trust policy, a permissions policy and an implicit deny are.

🔐 Module 3 · Secrets Manager & networking for databases

Secrets Manager

Database passwords never go in code or env vars. They live in a secret, and services fetch them at runtime. An RDS-style secret is a JSON document:

{ "engine": "postgres", "username": "agentadmin", "password": "•••", "host": "…cluster-xyz.us-east-1.rds.amazonaws.com",
  "port": 5432, "dbname": "agentdb", "dbClusterIdentifier": "tangerine-student1-aurora" }

ARN suffix

Secret ARNs end in a random 6-character suffix, e.g. …:secret:name-AbC123. Copy the full ARN, don't hand-type it.

Caller's permissions

The Data API reads the secret as you. Whoever calls ExecuteStatement needs GetSecretValue on that secret.

A secret is not a user

A secret only holds credentials. The DB role (CREATE ROLE …) and its GRANTs must exist inside PostgreSQL too.

Rotation

Secrets Manager can rotate passwords on a schedule. RDS can also manage the master password for you (manage_master_user_password).

Networking in five bullets

  • VPC: your private network. Subnets live in one AZ each. A DB subnet group needs subnets in at least 2 AZs.
  • Security groups: stateful firewalls on network interfaces (ENIs). Aurora's SG allows 5432 only from inside the VPC.
  • Private subnets have no route to the internet. Aurora doesn't need one.
  • The Data API is an AWS HTTPS endpoint, not a socket into your VPC. Our Lambda calls it from outside the VPC: no NAT, no VPC endpoints.
  • If you do put a Lambda in a VPC (to use a driver like psycopg), it then needs a NAT gateway or VPC endpoints for Secrets Manager, Bedrock and DynamoDB. A timeout instead of an error usually means a missing network path.
Exam lens An error comes back quickly → usually IAM, config or the database. A call hangs until timeout → usually networking (SG, route, endpoint). The symptom narrows down which hop to check.
LAB 1.4

Secrets Safari

⏱ 20 min🍊 Easy

🎯 See how the Data API uses secrets, and why a valid secret can still fail.

  1. Inspect both secrets' metadata. Note the 6-char ARN suffix: 
    aws secretsmanager describe-secret --secret-id "$ADMIN_SECRET_ARN" --query '{Name:Name,ARN:ARN,Rotation:RotationEnabled}'
aws secretsmanager describe-secret --secret-id "$KB_USER_SECRET_ARN" --query '{Name:Name,ARN:ARN}'
  2. Look at the admin secret's keys (don't paste the password anywhere): 
    aws secretsmanager get-secret-value --secret-id "$ADMIN_SECRET_ARN" \
  --query SecretString --output text | python3 -c 'import json,sys; print(sorted(json.load(sys.stdin)))'
  3. Run SQL through the Data API with the admin secret: 
    aws rds-data execute-statement --resource-arn "$CLUSTER_ARN" --secret-arn "$ADMIN_SECRET_ARN" \
  --database "$DB_NAME" --sql "SELECT current_user, version()" --format-records-as JSON \
  --query formattedRecords --output text
  4. Now try the bedrock_user secret. It's a perfectly valid secret… so why does it fail? 
    aws rds-data execute-statement --resource-arn "$CLUSTER_ARN" --secret-arn "$KB_USER_SECRET_ARN" \
  --database "$DB_NAME" --sql "SELECT current_user"
Why step 4 fails
The secret exists and you can read it, but the PostgreSQL role bedrock_user doesn't exist yet, so authentication fails. You create it in Lab 2.5. Lesson: secret OK + IAM OK ≠ database OK. The credentials must match a real DB user with the right GRANTs.
Step 3 prints agentadmin; step 4 fails with an authentication error, and you can explain why.

λ Module 4 · Lambda as the agent's tool runner

Zest is one Lambda function with an action router: the event's action field picks a tool. That's a common pattern for agent tool backends (Bedrock Agents calls them "action groups").

ACTIONS = {
    "health": health,
    "search_products": lambda e: search_products(e["query"], e.get("category"), ...),
    "remember": lambda e: remember(e["session_id"], e.get("role", "user"), e["content"]),
    "ask": lambda e: ask(e.get("session_id"), e["question"], e.get("customer_id")),
    ...
}

def handler(event, context=None):
    action = event.get("action", "health")
    try:
        result, ok = ACTIONS[action](event), True
    except ClientError as e:                       # AWS said no: return the code + message
        err = e.response["Error"]
        result, ok = {"error": err["Code"], "message": err["Message"]}, False
    log("agent_action", action=action, ok=ok, ...)  # one JSON line per call → CloudWatch
    return {"ok": ok, "action": action, "result": result}

Execution role

The identity for every AWS SDK call the code makes. Credentials are injected automatically.

Environment variables

Config: cluster ARN, secret ARN, table name, KB ID. A wrong value here is the #1 break-fix fault.

Timeout & memory

Zest: 120 s, 512 MB. A timeout shows up as Task timed out in logs, not as a clean error.

Layers

Extra libraries (our Anthropic SDK) mounted at /opt/python. boto3 ships with the runtime.

update-function-configuration --environment replaces ALL variables If you pass only the one you're fixing, every other variable is deleted. Edit in the console, or read-modify-write the full map (Lab 1.7 shows how).
LAB 1.5

Lambda Liftoff

⏱ 25 min🍊🍊 Medium

🎯 Invoke the agent's tools by hand, read its config, and make it fail on purpose.

  1. Read the function's configuration: 
    aws lambda get-function-configuration --function-name "$LAMBDA_NAME" \
  --query '{Runtime:Runtime,Timeout:Timeout,Memory:MemorySize,Role:Role,Layers:Layers[].Arn,Env:Environment.Variables}'
  2. Invoke with the raw AWS CLI. Note the StatusCode it prints before you read the JSON: 
    aws lambda invoke --function-name "$LAMBDA_NAME" \
  --cli-binary-format raw-in-base64-out \
  --payload '{"action":"search_products","query":"drone","category":"outdoor","limit":3}' \
  /tmp/zest.json && python3 -m json.tool /tmp/zest.json
  3. Try more tools with the labctl shortcut: 
    labctl invoke customer_profile '{"customer_id":"C00042"}'
labctl invoke search_products '{"query":"kettle","max_price":50}'
  4. Handled errors. Both of these come back with "ok": false and an error field, yet Lambda still returned StatusCode 200: the code caught the error. 
    labctl invoke search_products '{}'          # missing field → handled, ok:false
labctl invoke teleport                      # unknown action → handled, ok:false
  5. Make it fail on purpose: set the timeout to 1 second and ask Claude a question. Watch the log, then put it back with Terraform: 
    aws lambda update-function-configuration --function-name "$LAMBDA_NAME" --timeout 1 >/dev/null
aws lambda wait function-updated --function-name "$LAMBDA_NAME"     # config changes aren't instant
labctl invoke ask '{"question":"Which drones are best rated?"}'
(cd terraform && terraform apply -auto-approve)     # the reset button
What you should have seen
Handled errors still return HTTP 200 from Lambda with "ok": false: the code caught them. The 1-second timeout instead produces "errorMessage": "… Task timed out after 1.00 seconds" and a FunctionError: Lambda killed the code. Terraform noticed the drift (timeout: 1 → 120) and fixed it.
You've seen a success, a handled error, and a timeout, and you can tell them apart.

📈 Module 5 · CloudWatch: logs, metrics, alarms

Log groups

/aws/lambda/<fn> for Zest, /aws/rds/cluster/<id>/postgresql for Aurora (slow queries > 250 ms).

Structured logs

Zest prints one JSON object per event (agent_action, sql, tool_call), so Logs Insights can filter and aggregate on fields.

Metrics

Namespace + name + dimensions. AWS/Lambda Duration FunctionName=…. Use p90/p99, not just averages.

Alarms

Watch a metric against a threshold, then notify (SNS) or act. Handled errors are not Lambda Errors.

LAB 1.6

CloudWatch Mission Control

⏱ 30 min🍊🍊 Medium

🎯 Generate traffic, find it in logs, measure it with Logs Insights, and alarm on the errors that Lambda's metrics miss.

  1. Generate traffic: 
    for q in drone kettle tent lamp speaker router camera mug desk chair; do
  labctl invoke search_products "{\"query\":\"$q\"}" >/dev/null && echo "searched $q"
done
labctl invoke search_products '{}' >/dev/null   # one handled error
  2. Tail the logs live (Ctrl+C to stop): 
    aws logs tail "/aws/lambda/$LAMBDA_NAME" --since 10m --format short --follow
  3. In CloudWatch → Logs Insights, pick the Zest log group and run: 
    fields @timestamp, action, ok, duration_ms, error
| filter event = "agent_action"
| stats count(*) as calls, avg(duration_ms) as avg_ms, max(duration_ms) as max_ms by action, ok
    Then find your slowest SQL: 
    filter event = "sql"
| stats count(*) as n, avg(ms) as avg_ms, max(ms) as max_ms by statement
| sort avg_ms desc | limit 5
  4. Open the Mission Control dashboard ($DASHBOARD). Find your traffic spike.
  5. Handled errors don't increment Lambda Errors. Turn them into a metric, then alarm on it: 
    aws logs put-metric-filter --log-group-name "/aws/lambda/$LAMBDA_NAME" \
  --filter-name agent-handled-errors \
  --filter-pattern '{ $.event = "agent_action" && $.ok IS FALSE }' \
  --metric-transformations metricName=AgentHandledErrors,metricNamespace=Tangerine,metricValue=1,defaultValue=0

aws cloudwatch put-metric-alarm --alarm-name "$NAME-agent-errors" \
  --namespace Tangerine --metric-name AgentHandledErrors --statistic Sum \
  --period 60 --evaluation-periods 1 --threshold 1 \
  --comparison-operator GreaterThanOrEqualToThreshold --treat-missing-data notBreaching
  6. Trigger 3 handled errors, wait ~2 minutes, and watch the alarm go to ALARM: 
    for i in 1 2 3; do labctl invoke search_products '{}' >/dev/null; done
aws cloudwatch describe-alarms --alarm-names "$NAME-agent-errors" --query 'MetricAlarms[0].StateValue'
  7. Bonus: find Aurora's slow-statement log lines (the seed queries took > 250 ms): 
    aws logs filter-log-events --log-group-name "/aws/rds/cluster/$CLUSTER_ID/postgresql" \
  --filter-pattern '"duration:"' --max-items 5 --query 'events[].message'
The alarm …-agent-errors reached ALARM, and you can name the slowest agent action.

🍊 Module 6 · The PEEL break-fix method

Under a clock, people panic and change five things at once. Use PEEL instead, one fault at a time:

🔎

P · Probe

Reproduce it with the smallest call: health, one SQL statement, one get-item.

📜

E · Examine the error

Read it fully. Error code + action + resource usually name the hop and the fix.

🪜

E · Eliminate hops

Walk the request: invoke → role → config → secret → endpoint → DB. Which hop does the error point at?

🔒

L · Lock in & verify

Make one change, re-run the probe, confirm. Then move to the next fault, since there's often more than one.

BREAK-FIX 1.7

First Break-Fix: The Wrong Key

⏱ 20 min🍊🍊 Medium💥 labctl drill

🎯 Someone "tidied up" Zest's configuration and now it can't reach Aurora. Find the fault with PEEL and fix it without breaking anything else.

  1. Inject the fault (don't peek at what it does!): 
    labctl break wrong-secret
  2. Probe: labctl status. Which checks fail?
  3. Examine the full error text. Which action and which resource does it name?
  4. Eliminate: is it the role? The config? The secret? The database? (Your notes from Lab 1.3 step 4 will help.)
  5. Lock in the fix, then verify: 
    labctl check wrong-secret
Hint 1
The error mentions Secrets Manager. Which secret ARN is the Lambda configured to use? Compare it with $ADMIN_SECRET_ARN.
Hint 2: safe CLI edit of one env var
aws lambda get-function-configuration --function-name "$LAMBDA_NAME" \
  --query Environment.Variables > /tmp/env.json
python3 - <<'PY'
import json, os
p = "/tmp/env.json"; env = json.load(open(p))
env["DB_SECRET_ARN"] = os.environ["ADMIN_SECRET_ARN"]
json.dump({"Variables": env}, open(p, "w"))
PY
aws lambda update-function-configuration --function-name "$LAMBDA_NAME" --environment file:///tmp/env.json
aws lambda wait function-updated --function-name "$LAMBDA_NAME"
Solution & debrief

DB_SECRET_ARN pointed at the bedrock_user secret. The Lambda role can only read the admin secret, so the Data API call is denied.

Right fix: point DB_SECRET_ARN back at the admin secret (console: Lambda → Configuration → Environment variables).

Tempting wrong fix: granting the Lambda role access to the bedrock_user secret. IAM would then pass, but the login still fails: bedrock_user doesn't exist in PostgreSQL yet, and even after Lab 2.5 it has no privileges on products. You'd have widened permissions for nothing. Fix the cause, not the symptom.

labctl check wrong-secret shows 🏆 FIXED!

❓ Day 1 quiz

Zest's remember tool fails with "not authorized to perform: dynamodb:PutItem … because no identity-based policy allows". Where's the fix?

"No identity-based policy allows" means the role (an identity) needs an Allow for that action on that table. The trust policy only controls who can assume the role.

An identity policy Allows rds-data:ExecuteStatement, but an SCP explicitly Denies it. Result?

Explicit Deny anywhere in the evaluation chain overrides every Allow.

When Zest calls the RDS Data API with a secret ARN, whose permissions are used to read the secret?

The caller needs both rds-data:ExecuteStatement on the cluster and secretsmanager:GetSecretValue on the secret.

Why can Zest's Lambda run outside the VPC while Aurora sits in private subnets?

Data API requests go to an AWS service endpoint authorized by IAM. No network path into the VPC is needed.

Your handler catches an exception and returns {"ok": false}. What happens to the AWS/Lambda Errors metric?

Lambda only counts errors it sees (uncaught exceptions, timeouts). Lab 1.6 built a metric filter for the handled ones.

You run aws lambda update-function-configuration --environment Variables={KB_ID=abc123}. What else just happened?

--environment replaces the whole map. Edit in the console or read-modify-write all variables.
