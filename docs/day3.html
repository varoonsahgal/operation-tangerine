⚡ Module 1 · DynamoDB fundamentals

Items & keys

A table holds items (≤ 400 KB each). The primary key is a partition key, optionally plus a sort key. You design keys around access patterns.

Query vs Scan

Query reads one partition (PK =, SK conditions). Scan reads the whole table and filters afterwards, so you pay for everything it reads.

GSIs

An alternate key (e.g. customer_id), eventually consistent, with its own ARN: …/table/T/index/I.

TTL

A Number attribute holding epoch seconds. Expired items are deleted in the background, typically within a few days.

OperationWhat it doesZest uses it for
PutItemCreate/replace one item (optionally conditional)remember, set_state
GetItemRead one item by full key (strong or eventual)get_state (ConsistentRead)
QueryItems in one partition, SK range, orderedrecall: last N turns, newest first
UpdateItemChange attributes in place (atomic counters, SET/REMOVE)Counters, status flips
ScanRead everythingNever in the request path
TTL traps
  • A TTL value in milliseconds or as a String means the item never expires.
  • Expired-but-not-yet-deleted items still come back from reads. Filter on expires_at > :now if that matters.
  • After you disable TTL, you may have to wait up to an hour before you can re-enable it.
LAB 3.1

Design Agent Memory in DynamoDB

⏱ 30 min🍊🍊 Medium

🎯 Read the memory table's design, write a conversation by hand, and feel the difference between Query and Scan.

  1. Inspect keys, GSI and TTL: 
    aws dynamodb describe-table --table-name "$MEMORY_TABLE" \
  --query 'Table.{keys:KeySchema,gsi:GlobalSecondaryIndexes[].{name:IndexName,keys:KeySchema},mode:BillingModeSummary.BillingMode}'
aws dynamodb describe-time-to-live --table-name "$MEMORY_TABLE"
  2. Write a 2-turn conversation and a state item that expire in one hour: 
    EXP=$(( $(date +%s) + 3600 ))
put() { aws dynamodb put-item --table-name "$MEMORY_TABLE" --item "$1"; }
put '{"session_id":{"S":"sess-lab31"},"sk":{"S":"MSG#2026-11-25T09:00:00.000Z#000001"},"role":{"S":"user"},"content":{"S":"Hi, my kettle arrived dented"},"customer_id":{"S":"C00012"},"expires_at":{"N":"'$EXP'"}}'
put '{"session_id":{"S":"sess-lab31"},"sk":{"S":"MSG#2026-11-25T09:00:04.000Z#000002"},"role":{"S":"assistant"},"content":{"S":"Sorry! Sending a replacement."},"customer_id":{"S":"C00012"},"expires_at":{"N":"'$EXP'"}}'
put '{"session_id":{"S":"sess-lab31"},"sk":{"S":"STATE"},"status":{"S":"replacement_sent"},"customer_id":{"S":"C00012"},"expires_at":{"N":"'$EXP'"}}'
  3. Recall the newest message only (that's what recall does): 
    aws dynamodb query --table-name "$MEMORY_TABLE" \
  --key-condition-expression "session_id = :s AND begins_with(sk, :p)" \
  --expression-attribute-values '{":s":{"S":"sess-lab31"},":p":{"S":"MSG#"}}' \
  --no-scan-index-forward --limit 1 --query 'Items[].content.S'
  4. Find everything for a customer through the GSI: 
    aws dynamodb query --table-name "$MEMORY_TABLE" --index-name customer-index \
  --key-condition-expression "customer_id = :c" --expression-attribute-values '{":c":{"S":"C00012"}}' \
  --query 'Items[].[session_id.S, sk.S]' --output table
  5. Query vs Scan: compare Count, ScannedCount and consumed capacity: 
    aws dynamodb scan --table-name "$MEMORY_TABLE" --filter-expression "customer_id = :c" \
  --expression-attribute-values '{":c":{"S":"C00012"}}' --return-consumed-capacity TOTAL \
  --query '{count:Count,scanned:ScannedCount,rcu:ConsumedCapacity.CapacityUnits}'
  6. Idempotency: write turn #1 again with a condition. What happens? 
    aws dynamodb put-item --table-name "$MEMORY_TABLE" --condition-expression "attribute_not_exists(sk)" \
  --item '{"session_id":{"S":"sess-lab31"},"sk":{"S":"MSG#2026-11-25T09:00:00.000Z#000001"},"role":{"S":"user"},"content":{"S":"dupe"}}'
What to notice
The Scan reads every item in the table (ScannedCount > Count, and the gap grows with the table) and you pay for all of them. The Query touches only one partition. Step 6 fails with ConditionalCheckFailedException, which is how you stop duplicate writes when a Lambda retries.
You can describe the table's key design in one sentence: "one partition per session; sort key orders turns by time; GSI by customer; TTL cleans up."

  • Why DynamoDB for conversation memory? Single-digit-millisecond reads and writes at any scale, one partition per session (traffic spreads out), TTL for free cleanup, and simple IAM scoping.
  • Sort keys that sort: ISO-8601 timestamps sort lexically in time order, so ScanIndexForward=false + Limit gives you "last N turns".
  • Bound the context: load a window, not the whole history; summarize older turns into a SUMMARY# item.
  • Managed option: Amazon Bedrock AgentCore Memory gives you a managed short/long-term memory service. Know it exists, but the exam's focus is DynamoDB.

🔌 Module 3 · Model Context Protocol & the AWS MCP servers

MCP is an open protocol that lets AI applications use external tools and data through small servers. A host (Kiro, VS Code, Claude Code, Amazon Q Developer…) runs an MCP client per server. Each server exposes tools (functions), resources (data) and prompts.

MCP debugging checklist
  1. Valid JSON (no trailing commas!) and the right top-level key for your client.
  2. uvx is on the PATH the IDE sees. GUI apps often don't inherit your shell PATH, so use the full path from which uvx.
  3. --resource_arn is the cluster ARN; --database is agentdb, not postgres.
  4. Region matches where the resources live, for both servers.
  5. The profile's identity can call rds-data:ExecuteStatement, read the secret, and read DynamoDB.
  6. The Data API is enabled. The Postgres MCP server uses it too.
  7. Flag names change between versions: run uvx awslabs.postgres-mcp-server@latest --help to see yours.

🏎️ Module 4 · Query optimization for agent tools

Agent tools run the same few queries thousands of times, with a model waiting on each one. A 300 ms query called 4 times per answer is over a second of waiting. That's why the exam has an objective on optimizing the agent's queries.

EXPLAIN

Shows the plan. EXPLAIN (ANALYZE, BUFFERS) runs it and shows real timings and I/O (careful with writes!).

Scan types

Seq Scan (every row) · Index Scan · Index Only Scan · Bitmap Index + Heap Scan (many matches).

B-tree limits

Great for =, ranges, sorting and LIKE 'abc%'. Useless for a leading wildcard ILIKE '%abc%'.

pg_trgm + GIN

Splits text into 3-letter grams. USING gin (name gin_trgm_ops) makes ILIKE '%drone 42%' index-assisted.

Composite index column order

For WHERE category = :c ORDER BY rating DESC LIMIT 10, put equality columns first, then the sort columns: (category, rating DESC, product_id). Postgres jumps straight to the category, reads rows already in rating order, and stops after 10 matches: no sort, no full scan.

LAB 3.6

Optimize Product Search

⏱ 40 min🍊🍊🍊 Exam-critical

🎯 Measure Zest's product search, explain why it's slow, add the right two indexes, and prove the improvement.

  1. Baseline latency, end to end, through the agent: 
    for q in "drone 42" "speaker" "kettle 7" "tent" "smart watch"; do
  labctl invoke search_products "{\"query\":\"$q\"}" | python3 -c 'import json,sys; r=json.load(sys.stdin); print(r["duration_ms"], "ms", len(r["result"]), "rows")'
done
  2. Explain both query shapes the tool generates: 
    labctl sql "EXPLAIN ANALYZE SELECT product_id, name, price, rating FROM products WHERE name ILIKE '%drone 42%' ORDER BY rating DESC, product_id LIMIT 10"
labctl sql "EXPLAIN ANALYZE SELECT product_id, name, price, rating FROM products WHERE name ILIKE '%speaker%' AND category = 'audio' ORDER BY rating DESC, product_id LIMIT 10"
    Find Seq Scan on products and Rows Removed by Filter.
  3. Before you look at the solution: which index would help each query, and why wouldn't a plain b-tree on name help?
  4. Create your indexes (the Query Editor or labctl sql). Re-run step 2 after each one and watch the plan change.
  5. Re-run step 1 and compare. Then in Logs Insights: 
    filter event = "sql" and statement like /FROM products/
| stats count(*) as n, avg(ms) as avg_ms, pct(ms, 90) as p90_ms by bin(5m)
  6. Bonus: find the heaviest queries overall: 
    labctl sql "CREATE EXTENSION IF NOT EXISTS pg_stat_statements"
labctl sql "SELECT calls, round(mean_exec_time::numeric, 2) AS mean_ms, left(query, 70) AS query FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5"
  7. Grade it: labctl check slow-search
Solution (also in sql/03_indexes_solution.sql)
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_products_name_trgm       ON products USING gin (name gin_trgm_ops);       -- leading-wildcard ILIKE
CREATE INDEX idx_products_category_rating ON products (category, rating DESC, product_id); -- filter + sort + LIMIT
ANALYZE products;

Expect roughly 35 ms → under 1 ms per query on a laptop-sized Postgres. A 0.5-ACU Aurora starts slower, so your gain will be bigger.

Both plans show index use (Bitmap Index Scan on idx_products_name_trgm / Index Scan on idx_products_category_rating) and labctl check slow-search is 🏆.

❓ Day 3 quiz

Best way to load "the last 10 turns of session S, newest first"?

One partition, sort key in time order, read backwards, stop at 10.

Memory items never expire, even though TTL is enabled on expires_at. Most likely cause?

TTL needs a Number of epoch seconds. Milliseconds look like a date thousands of years away.

Query on customer-index fails with AccessDenied, but the policy allows dynamodb:Query on the table ARN. Fix?

Indexes are separate IAM resources.

In the Aurora PostgreSQL MCP server config, --resource_arn should be…

It talks to the Data API, which works on the cluster.

Which index lets WHERE name ILIKE '%drone 42%' avoid a full scan?

Trigram GIN indexes support substring and ILIKE matching. B-trees can't serve leading wildcards.

Best index for WHERE category = $1 ORDER BY rating DESC LIMIT 10?

Equality first, then the sort column. The scan stops after 10 rows with no sort step.

An MCP server launched by your IDE with uvx talks to the IDE over…

Local servers are child processes speaking JSON-RPC over stdin/stdout. Remote servers use Streamable HTTP.
